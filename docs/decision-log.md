# Architecture decision log

This log consolidates the architecture sketch and observed source decisions. “Implemented” records the prototype choice, not an enterprise approval. Proposed extensions require the accountable roles and phase gates in the [roadmap](delivery-roadmap.md). Requirements and risk IDs are in [traceability](requirements-traceability.md). ADR-01–04 retain the intent of the earlier architecture sketch.

| Decision / status / accountable role | Choice and rationale | Alternatives considered | Tradeoffs, consequences and revisit trigger |
| --- | --- | --- | --- |
| **ADR-01 Bounded orchestration with human approval** — implemented; operations owner | Fan out demand/inventory, then allocation, then risk/value; deterministic policy and expiring approval precede receipt creation. Supports R-01, R-02, C-02. | Manual serial analysis; one unconstrained agent; autonomous execution | Parallelism reduces dependency wait but adds failure coordination. Approval adds queue time; risk model is advisory, not authority. Revisit workflow infrastructure when pilot requires long-running tasks; retain business approval unless separately authorized. |
| **ADR-02 Separate evidence from authority** — implemented boundary, proposed enterprise adapters; security/data owners | Models return strictly validated fields; server controls routing; deterministic value and execution cannot be model-routed. Models have no tools or retail permissions. Supports R-04, C-01, C-03. | Model-selected arbitrary tools; direct database writes; treating model narrative as verified evidence | Restricts flexibility and requires adapter engineering, but prevents model output granting itself permission. Production reads need source verification and writes need scoped authorization, current-state checks and idempotency. Revisit only with operation-specific safety evidence. |
| **ADR-03 Version evidence and policy for reproducibility** — proposed; governance owner | Attach source IDs/timestamps, effective policy versions, retrieval citations, model deployment/version, prompt/config version and approval revision to each decision. Supports R-04, C-04. | Unversioned prompts; logs alone; broad unfiltered document retrieval | Adds storage, data stewardship and access-filter testing. Current traces and synthetic rationales are insufficient; reproducibility means reconstructable inputs, not guaranteed identical stochastic output. Revisit retention and retrieval design after classification and pilot evidence. |
| **ADR-04 Measure outcomes as well as model quality** — proposed measurement process; product/finance owners | Establish a baseline and bounded comparison cohort; measure decision time, service, net benefit, adoption, overrides and costs together. Supports R-02, R-03, C-07. | Dashboard fixtures as ROI; model accuracy alone; approval rate as success | Requires event instrumentation and finance attribution; seasonal effects and selection bias can obscure results. Current deterministic unit economics are illustrative. Expand only on observed value and safety; do not optimize approval acceptance at the expense of warranted rejection. |
| **ADR-05 Simple state now, durable actions later** — Blob/ETag implemented, durable workflow proposed; service owner | Use in-memory local state and deployed Blob compare-and-swap for short demo runs. Claim approval before receipt creation. Supports C-02, C-04, C-05. | Relational transaction store; durable queue/workflow engine from day one; stateless approval | Low prototype footprint, but crashes can strand runs and audit is mutable. Before real writes, add durable stages, client recovery keys, transactional outbox or equivalent, target idempotency, reconciliation and compensation. A stronger store alone cannot guarantee exactly-once external effects. |
| **ADR-06 Separate user and workload identity** — demo implementation, pilot evolution proposed; security owner | Easy Auth plus application role/scope/owner checks for users; explicit managed identity for models/storage. Supports C-03. | API keys; shared service user; client-only authorization | Removes embedded keys but hosted header trust/RBAC must be verified. Manual token entry, broad host-storage role and same-owner approval remain demo limitations. Pilot needs MSAL sign-in, scoped workload identities, team permissions and separation of duties where required. |
| **ADR-07 Minimize prototype footprint; budget by phase** — implemented demo configuration; platform/finance owners | One Functions app serves UI/API; bounded calls, shared run cap and budget notifications; no required search or agent platform. Supports R-07, C-05. | Separate paid frontend/backend tiers; provisioned model throughput; enterprise platform stack immediately | Lower fixed cost trades away durable orchestration, reserved capacity and advanced integration controls. Alerts are not hard caps; admission limits exclude some hosting costs. Add search, gateways, private networking or reserved capacity only with evidenced requirements and revised TCO. |
| **ADR-08 Keep internal contracts explicit; qualify platform migration** — implemented internal protocol, proposed Foundry path; architecture owner | Retain `retail-task/2`; use the existing Azure OpenAI-compatible adapter as the first model integration seam. Qualify retrieval and governed tools separately. Supports C-01, C-07. | Claim A2A compatibility from JSON envelopes; immediate rewrite onto hosted agent service; arbitrary provider substitution | Keeps dependency and debugging scope small but provides no official A2A interoperability or Foundry Agent Service lifecycle. New endpoints/models need compatibility, security and evaluation checks. Adopt an external protocol only for a concrete interoperability need and after conformance testing. |

## Review discipline

Before G1, named owners confirm or supersede these choices with evidence and an approval date. Before G2, review all proposed extensions and unresolved risks. Changes to data use, model/provider, policy, external write authority or retention reopen the affected decision and acceptance tests. Record a new decision or explicit supersession rather than silently rewriting past approvals. No production architecture acceptance is recorded here.
